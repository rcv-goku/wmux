# W1-1a: the v2 control plane

wmux now serves the cmux v2 protocol on a per-user control pipe, keeps the legacy wmux JSON
protocol working on that pipe and on the old `wmux-ipc-<pid>` pipe, and runs as one instance
per channel. ARCHITECTURE.md ADR-2.4, ADR-2.6 and ADR-3.1 to ADR-3.7 are the reference.

## Pipes and discovery

| Pipe | Name | Serves |
|---|---|---|
| control | `\\.\pipe\wmux-<channel>-<sidhash8>-s<session>` | cmux v2 JSON, legacy wmux JSON (sniffed per line) |
| launch | control name + `-launch` | `app.launch` only; on even with `socket-control = off` |
| legacy | `\\.\pipe\wmux-ipc-<pid>` | legacy wmux JSON only (one release, removed at M3) |

- `channel` is `stable` (release builds) or `debug` (debug builds), `-Dwmux-channel=<name>` at
  build time, `dev-<tag>` with `WMUX_TAG`, or `WMUX_CHANNEL`. `sidhash8` is the first 4 bytes
  of SHA-256 of the user SID in hex; `session` is the logon session.
- Every pipe is current-user only (DACL with the user SID, remote clients rejected).
- When the control name is already taken (another user squats it, or an instance could not be
  handed a launch), the instance serves `<name>-alt-<8hex>` and records it in the marker.
- `STATE\run\instance.json` (`WMUX_STATE_DIR`, else `%LOCALAPPDATA%\wmux\<channel>`) names the
  pipes: `{pipe, launch_pipe, pid, exe, version, protocol: 2, channel, boot_id, started_at}`.
  It is replaced atomically at startup and deleted on exit while it still names the process.
  `cmux`/`wmux.com` find the instance through it when no `WMUX_SOCKET_PATH`/`CMUX_SOCKET_PATH`
  is set.

## Single instance

Starting `wmux.exe` while an instance of the same channel runs hands the launch over and
exits 0: folders and files on the command line open as new workspaces (`app.launch
{intent:"open"}`), a `wmux:`/`cmux:` URI is passed on (`intent:"uri"`, not acted on yet), and a
bare launch opens a new window (`intent:"new_window"`). The launching process lets the instance
come to the foreground. Options (`--…`, `+…`) on the second command line are ignored.

## Protocol

- Requests are one JSON object per line: `{"id", "method", "params"}`; replies are one line,
  `{"id","ok":true,"result"}` or `{"id","ok":false,"error":{code,message,data?}}`, in request
  order per connection. Pre-dispatch errors use cmux's codes and strings (`invalid_utf8`,
  `parse_error "Invalid JSON"`, `invalid_request "Expected JSON object"` / `"Missing method"`,
  `method_not_found "Unknown method"`).
- Selector keys must be canonical: `workspaceId`, `surfaceID`, `tabId`… fail with
  `invalid_params "Unsupported parameter '<x>'; use '<canonical>'"`. Every `*_id` takes a UUID,
  a ref (`workspace:2`, `tab:3` = `surface:3`) or a 0-based index; a workspace index is the
  sidebar display position. A selector that does not resolve fails with `not_found`
  (`Workspace not found`, `Surface not found for the given surface_id`) and never falls back.
  Without selectors the target is the `params.caller` context, else the most recently
  activated wmux window.
- Admission (cmux numbers): 64 live connections, 64 more wait up to 15 s and are served in
  arrival order, the rest get `overloaded {retryable:true, retry_after_ms, reason}` (reasons
  `pool_saturated`, `pending_expired`, `preauthorization_saturated`, `accept_buffer_full`,
  `server_stopping`). Polling methods share a per-connection token bucket (burst 9, one per
  100 ms) and get `rate_limited {retry_after_ms}`.
- Deadlines: UI-thread methods have 10 s. A request that never ran times out with `timeout
  {stage:"main_actor", deadline_ms, retryable:true}`, one that was running with
  `retryable:false` (its late result is dropped). While a menu, message box or other modal
  loop runs, mutating requests wait (their deadline keeps running).
- Lines up to 16 MiB; a longer line gets `invalid_request "Request too large"`.

## Methods

- `system.ping` → `{pong:true}`.
- `system.capabilities` → `{protocol:"cmux-socket", version:2, socket_path, access_mode,
  capabilities:{wmux:{version, build, channel, platform:"windows"}}, methods:[sorted]}`.
- `wmux.debug.*` exist only in test mode (`WMUX_TEST_MODE=1`): `ready`, `app.quit`,
  `dialogs.list`, `dialogs.answer`, `clipboard.get`, `clipboard.set` (the fake clipboard),
  `focus_state`, `layout`, `type`, `key`, `menu.list`, `menu.invoke`, `timers`,
  `external_open.list`, `sounds.list`. Features add their own in `features/<id>/debug.zig`.

## Legacy protocol

All 37 legacy commands keep their request and reply shapes byte for byte on the control pipe
and on `wmux-ipc-<pid>`, which now serves many clients at once. `socket-control = read-only`
refuses non-read commands before any side effect (also before `workspace-new --worktree`
runs `git worktree add`); `socket-control = off` starts neither pipe (the launch pipe stays).

## Windows notes and limits

- Access modes (`automation.socketControlMode`, `cmuxOnly` as the default, the capability
  token and password mode) and the text-v1 protocol arrive with W1-1b; until then the control
  pipe admits any process of the same user (the `automation` mode), and a line that is neither
  v2 nor legacy JSON gets the legacy parser's error reply.
- `surface.read_text` is answered by a hidden stand-in over the legacy `read-screen` until
  W2-3 registers the method (it is not listed in `system.capabilities`).
- `wmux.debug.*` is not served in debug builds without `WMUX_TEST_MODE`.
