# Terminal environment, PATH, jobs and shell integration (W1-3)

Every wmux terminal tells the processes in it which workspace and surface they run in and how to
reach this wmux instance (ARCHITECTURE.md ADR-3.9). This page covers the protected `CMUX_*` /
`WMUX_*` environment, `PATH` and `WSLENV`, the instance and per-tab job objects, the agent
shims directory and the shell-integration fixes. The feature is `features/env_identity`; the
pure rules are in its `logic/` files.

## Protected environment

Applied **last** to every terminal spawn (`termio/Exec.zig`), after the inherited environment,
Ghostty's own variables, shell integration, the Ghostty `env = ...` configuration and any
workspace or layout env, so none of those can replace them:

| Variable | Value |
|---|---|
| `CMUX_WORKSPACE_ID`, `WMUX_WORKSPACE_ID` | workspace UUID |
| `CMUX_SURFACE_ID`, `WMUX_SURFACE_ID`, `CMUX_PANEL_ID` | tab (surface) UUID |
| `CMUX_TAB_ID` | the **workspace** UUID (cmux legacy meaning) |
| `CMUX_PANE_ID`, `WMUX_PANE_ID` | pane UUID at spawn |
| `CMUX_TERMINAL_LIFECYCLE_ID`, `WMUX_TERMINAL_LIFECYCLE_ID` | new UUID per spawn |
| `CMUX_SOCKET_PATH`, `WMUX_SOCKET_PATH` | control pipe `\\.\pipe\wmux-<channel>-<sidhash8>-s<session>` (the v2 server's own name once it runs; the computed name before) |
| `CMUX_SOCKET` | empty (deprecated alias; an inherited value cannot shadow the path). cmd.exe drops empty variables, so it reads as unset there |
| `CMUX_SOCKET_CAPABILITY`, `WMUX_SOCKET_CAPABILITY` | the capability token, once W1-1b provides one |
| `CMUX_SOCKET_PASSWORD` | only when wmux itself was started with `WMUX_SOCKET_PASSWORD` or `CMUX_SOCKET_PASSWORD` |
| `CMUX_BUNDLE_ID`, `WMUX_BUNDLE_ID` | `wmux.app` (stable channel) or `wmux.app.<channel>` |
| `CMUX_BUNDLED_CLI_PATH`, `WMUX_BUNDLED_CLI_PATH` | `INSTALL\cli\cmux.exe` |
| `CMUX_SHELL_INTEGRATION_DIR` | `SHARE\wmux\shell-integration` when it exists, else Ghostty's `share\ghostty\shell-integration` (where dev and release builds install the scripts today) |
| `CMUX_PORT`, `CMUX_PORT_END`, `CMUX_PORT_RANGE` | the workspace's port block (below) |
| `TERM` | `xterm-256color`, unless the Ghostty `term` key is set in the configuration (then Ghostty's value; WSL distros and ssh hosts lack `xterm-ghostty`) |
| `COLORTERM`, `TERM_PROGRAM`, `TERM_PROGRAM_VERSION` | `truecolor`, `ghostty`, the wmux version |

`GHOSTTY_PID`, `GHOSTTY_SURFACE_ID` and `GHOSTTY_BIN_DIR` are unchanged. Running terminals keep
the environment they were started with.

### Port blocks

The first terminal of a workspace gives it the next ordinal (0, 1, 2, ... while the app runs).
Its terminals get `CMUX_PORT = automation.portBase + ordinal * automation.portRange`,
`CMUX_PORT_END = CMUX_PORT + portRange - 1` and `CMUX_PORT_RANGE = portRange`. Defaults: base
9100, range 10, so the first workspace has 9100-9109 and the second 9110-9119. Blocks never go
past port 65535; the ordinals wrap around to the first block instead.

## Base environment: credentials, PATH, WSLENV

- `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `ANTHROPIC_SMALL_FAST_MODEL`, `CLAUDE_CODE_USE_BEDROCK`
  and `CLAUDE_CODE_USE_VERTEX` inherited by wmux are removed from new terminals. Set
  `"wmux": { "agents": { "preserveAuthEnv": true } }` in `wmux.json` to keep them. A Ghostty
  `env = ANTHROPIC_API_KEY=...` line still applies (it is not inherited).
- `PATH` starts with `INSTALL\cli` (so `wmux` and `cmux` resolve to the bundled CLI before any
  other copy) and, while an agent integration is enabled, `STATE\shims\<build-id>\agents` before
  it. The old append of `INSTALL` at the end stays. The installer still never touches the
  system or user PATH.
- `WSLENV` keeps its inherited entries and adds `CMUX_WORKSPACE_ID/u CMUX_SURFACE_ID/u
  CMUX_PANEL_ID/u CMUX_TAB_ID/u CMUX_PANE_ID/u CMUX_TERMINAL_LIFECYCLE_ID/u CMUX_SOCKET_PATH/u
  CMUX_SOCKET_CAPABILITY/u CMUX_BUNDLED_CLI_PATH/up TERM_PROGRAM/u` and the `WMUX_*` twins
  (plus `CMUX_SOCKET_PASSWORD/u` when set), so `wsl.exe` started from a wmux terminal sees the
  ids (the CLI path translated to `/mnt/<drive>/...`).

## Settings

| Key | Type | Default | Effect |
|---|---|---|---|
| `automation.portBase` | integer 1-65535 | 9100 | first port of the workspace port blocks |
| `automation.portRange` | integer 1-65535 | 10 | ports per workspace |
| `wmux.agents.preserveAuthEnv` | boolean | false | keep the inherited Anthropic credentials in terminals |

All apply to terminals started after the change.

## Job objects

- At startup wmux puts itself in an unnamed **instance job** whose only limit is
  `JOB_OBJECT_LIMIT_BREAKAWAY_OK`. Every process wmux starts afterwards is in it.
- Every terminal spawn creates a **per-tab job** (`BREAKAWAY_OK` only, never
  `KILL_ON_JOB_CLOSE`) and starts the shell in it through `PROC_THREAD_ATTRIBUTE_JOB_LIST`, next
  to the pseudoconsole attribute. Windows nests it under the instance job, so the shell and every
  descendant that does not break away are in both, even after their parent exits.
- Closing a tab closes its job handle and never kills anything through the job. Processes that
  share the tab's console (a `start /b` child, for example) still end with the pseudoconsole,
  because Windows terminates the clients of a closed pseudoconsole; processes with their own
  console or none (GUI apps, `CREATE_NO_WINDOW` tools) keep running.
- If the job attribute is refused or the spawn fails with it (a parent job that forbids nesting),
  the terminal starts without a job and the log says so; caller identification then falls back
  to process ancestry and the capability token (W1-1b).
- The jobs answer `inInstanceJob(pid)` (the `cmuxOnly` socket check), `surfaceForPid(pid)` (the
  caller context of a CLI client) and `processIds(surface)` (`wmux.debug.layout`
  `surface.pids`, later `top`/`memory`).

The log line `spawn identity workspace=... surface=... pane=... lifecycle=... job=tab|none` in
`STATE\logs\wmux.log` records every spawn.

## Agent shims directory

At startup `STATE\shims\<build-id>\agents` is created (build id = the version string mapped to
`[a-z0-9-]`) with a `.wmux-shims` sentinel in `STATE\shims\<build-id>\`, and every other
`STATE\shims\<id>` directory that has a sentinel is deleted (directories without one are left
alone). W3-2 puts the agent wrappers (`claude.exe`, `codex.exe`, ...) there; no agent integration
exists yet, so the directory is not on PATH until then.

## Shell integration

- **cmd.exe** (the default shell): when `PROMPT` is unset or cmd's default `$P$G`, terminals get
  `PROMPT=$e]9;9;$P$e\$e]133;A$e\$P$G$e]133;B$e\`, which reports the working directory
  (OSC 9;9) and marks the prompt (OSC 133 A/B). A custom `PROMPT` or a `prompt` command wins.
- **Git Bash / MSYS**: `bash.exe` and `zsh.exe` (any case, with or without `.exe`) get the bash
  and zsh integration. `C:\Windows\System32\bash.exe` is the WSL launcher and gets none; a bare
  `bash` counts as the launcher when that file exists, because Windows resolves it there first.
  The integration puts `cli\posix` (the `cmux`/`wmux` sh launchers, release layout) first on
  PATH. The bash and zsh scripts are checked out with LF line endings on every machine.
- **PowerShell**: the integration script works in Windows PowerShell 5.1 (no `` `e `` escapes),
  and the user's arguments now go before `-NoExit -Command`, so `powershell.exe -NoProfile`
  really skips the profile. A command line that already runs `-Command`/`-File` gets no
  integration.

## Known limitations

- `CMUX_SOCKET_CAPABILITY` is exported once W1-1b provides the token.
- Dev builds (`zig build`) install neither `cli\wmux.exe` nor `cli\posix\` (release staging
  does); `where wmux` then lists the extensionless `cli\wmux` launcher first.
- No build installs `SHARE\wmux\shell-integration` yet, so `CMUX_SHELL_INTEGRATION_DIR` names
  Ghostty's `share\ghostty\shell-integration`.
