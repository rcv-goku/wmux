# Settings layer (W1-4a)

wmux reads its settings from JSONC files in the cmux format and layers them over the Ghostty
configuration (ARCHITECTURE.md ADR-5). This page covers the app side: files, precedence, live
reload, the Ghostty overlay and overrides, managed policy and error notices. The offline
`config` CLI is W1-4b.

## Files and precedence

Lowest first; a higher layer wins key by key (object settings merge key by key).

| # | Layer | Where |
|---|---|---|
| 1 | spec defaults | `src/wmux_proto/settings/specs/*.zig` |
| 2 | legacy Ghostty keys | only keys written in the Ghostty config (`window-show-sidebar`, `window-sidebar-width`, `sidebar-metadata`, `window-show-right-sidebar`, `window-right-sidebar-width`, `socket-control`, `desktop-notifications`); defaults never count |
| 3 | shared cmux.json | `%XDG_CONFIG_HOME%\cmux\cmux.json`, else `%USERPROFILE%\.config\cmux\cmux.json` |
| 4 | wmux.json | `%WMUX_CONFIG_DIR%\wmux.json`, else `%XDG_CONFIG_HOME%\wmux\wmux.json`, else `%USERPROFILE%\.config\wmux\wmux.json` |
| 5 | packs | `"packs": ["dir-or-file", {"path": "..."}]` in a file load just below that file (a directory resolves to `wmux.pack.json`, then `cmux.pack.json`; relative to the listing file; http(s) entries are refused with a warning) |
| 6 | project file | upward from the app's working directory, stopping below `%USERPROFILE%`: `.wmux\wmux.json`, `wmux.json`, `.cmux\cmux.json`, `cmux.json`; only project-scoped keys apply, and `actions` / `commands` entries override global ones with the same id (or `name`) |
| 7 | managed policy | `HKLM\Software\Policies\wmux`, then `HKCU\...`: one value per setting path (`REG_SZ` JSON literal or `REG_DWORD`); a policy value locks the key |

A value with the wrong type or out of range falls back to the next lower layer and is logged
(`settings value rejected ...`) and listed in the `settings.invalid_values` notice. `schemaVersion`
newer than 1 is parsed best effort with a warning.

## Live reload

A watcher thread watches the directory of every file above, of the Ghostty config files
(default files, `--config-file` and includes) and of the overlay, following symlinks to their
targets. A save reloads about 300 ms after the last write; saves that leave the bytes unchanged
do nothing. Each successful reload is a new revision; `STATE\logs\wmux.log` gets

```
settings reloaded rev=2 source=wmux.json changed=1
settings key automation.socketControlMode="allowAll" source=wmux.json
```

(`source` names the files that changed: `cmux.json`, `wmux.json`, `pack`, `project`, `policy`,
`ghostty`, `manual`). Features receive `onSettingsChanged(diff)` and the events
`wmux.settings.changed` (`changed_keys`) and `config.reloaded` are emitted.

A JSONC syntax error keeps the last good settings: the log gets
`settings reload failed source=wmux.json errors=1; keeping rev=2` and the window shows the
`settings.parse_error` notice with the first three errors (`wmux.json:5:3: expected ',' or '}'`)
and an Open button. Fixing the file reloads the next revision and removes the notice.

Reload Configuration (`reload_config`, Ctrl+Shift+,) reloads the Ghostty files and every JSON
layer.

## Ghostty overlay and overrides

After the Ghostty configuration (unchanged locations, CLI and includes) wmux loads
`CONFIG\config.ghostty` (the wmux overlay) and then `STATE\run\settings-overrides.ghostty`, which
the settings layer generates: one line per JSON setting set in a file or by policy whose spec maps
to a Ghostty key, e.g. `terminal.copyOnSelect` -> `copy-on-select = true`,
`terminal.confirmUnsafePaste` -> `clipboard-paste-protection`. Unset JSON keys defer to Ghostty.
When the overrides change, Ghostty reloads once (`ghostty config reloaded reason=settings-overrides`);
an edited Ghostty file reloads it too (`reason=file`). Ghostty diagnostics show the
`ghostty.config_errors` notice with the first three, once per distinct set.

## Policy

Policy is re-read on registry change notifications for `Software\Policies`, and every 60 s. In
test mode `WMUX_TEST_POLICY_FILE` names a JSON file used instead of the registry:
`{"HKLM": {"automation.socketControlMode": "allowAll"}, "HKCU": {...}}` (or a flat object = HKLM;
`{"dword": n}` stands for a `REG_DWORD`).

## Notices

Notices appear in a panel at the top right of every window, one row per notice with its action
and a close button. The panel never takes focus. Each notice is also logged
(`notice <id>: <title> <body>`).

## Windows notes

- Keys the settings layer needs before their owning features declare specs
  (`automation.socketControlMode`, `terminal.copyOnSelect`, `terminal.confirmUnsafePaste`) are
  resolved from interim specs; the owner's spec replaces them automatically.
- The project layer follows the app's working directory; per-workspace project settings come with
  the workspace features.
