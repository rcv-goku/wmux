## What
`App.run` asks the session feature before creating the default window:

```diff
--- a/src/apprt/win32/App.zig
+++ b/src/apprt/win32/App.zig
@@ pub fn run(self: *App) !void {
-    const window = try alloc.create(Window);
-    errdefer alloc.destroy(window);
-    try window.init(self, .{});
-    try self.windows.append(alloc, window);
-    _ = try window.addTab();
+    // A pending session restore creates the windows itself (hidden first,
+    // placed, then shown; ADR-9.4). Otherwise one window with one tab.
+    if (!session_api.restoreOnLaunch(self)) {
+        const window = try alloc.create(Window);
+        errdefer alloc.destroy(window);
+        try window.init(self, .{});
+        try self.windows.append(alloc, window);
+        _ = try window.addTab();
+    }
```

`features/session/api.zig` then gains `restoreOnLaunch(app) bool` (true when it created at least
one window) calling `restore.apply` synchronously with window creation instead of re-keying.

## Why
persistence-session-restore-on-launch (ADR-9.4): "create windows hidden and fit placement with
SetWindowPlacement ...; restore replaces state; it never appends into window 0". App.run is
frozen and creates window 0 with a default terminal before the message loop starts; no
registry, hook or event runs between `features.init` and that window. The stub works but
spawns one shell that is killed a few milliseconds later and shows window 0 before its
placement is final.

## Stub until merged
As described above (restore.zig `runLaunch`). Window 0 is still created at the saved
placement (ui/placement.zig asks `session.api.pendingFirstPlacement`), and the exact clamped
placement is applied by the restore task.

## Impact and risks
W1-1a owns the App.zig edits of this wave; the change is three lines and independent of the
logger lines. A failing restore must fall back to the default window (the api function
returns false).
